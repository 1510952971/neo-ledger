# Neo Ledger 运维与灾备运行手册

这是上线前的可执行模板。托管环境必须把负责人、值班电话和具体域名补齐后再签字。

## 初始 SLO

| 指标 | 目标 | 告警阈值 |
| --- | ---: | ---: |
| 核心 API 可用性 | 99.9% / 月 | 5 分钟错误率 > 2% |
| 同步成功率 | ≥99.5% | 15 分钟 < 99% |
| 写操作 P95 | <1 秒 | 连续 10 分钟 >2 秒 |
| 备份 RPO | ≤24 小时 | 超过 26 小时无成功备份 |
| 恢复 RTO | ≤4 小时 | 演练超过 3 小时 |

## 发布前检查

1. `npm ci && npm audit --omit=dev --audit-level=high && npm run lint && npm test`。
2. 生成 SBOM，保存 commit、镜像 digest、构建日志和校验值。
3. 检查 `DEPLOYMENT_MODE`、HTTPS、可信 Host、邮件、备份和 `NEO_WEBDAV_ALLOWED_HOSTS`。
4. 在隔离数据库执行迁移、导入、导出、恢复和回滚；确认旧版本仍能读取备份。
5. 分 5%/20%/50%/100% 放量，每级观察至少 48 小时。

发布后将 `/api/health` 配置为负载均衡器或容器编排的 readiness probe：仅 `200` 且 JSON 中 `status=ok`、`checks.database=ok`、`checks.schema=ok` 时接收流量；`503` 时摘除节点并保留 `X-Request-ID` 供排障。不要使用它替代业务成功率、同步成功率或备份时效监控。

仓库提供 `.github/workflows/restore-rehearsal.yml`：每月首日自动运行一次，也可通过 GitHub Actions 手动触发。它在隔离的 Node/D1 shim 数据库上执行完整 `npm run test:api`，覆盖备份、恢复、预检、暂存、回滚和权限边界，并把日志保存 90 天。该工作流证明仓库内恢复协议仍可执行，但不能替代生产备份介质、真实 D1、跨版本和 RPO/RTO 演练；每次演练仍需由值班工程师补充生产环境报告和签字。

## 每月恢复演练

1. 从生产备份复制到隔离环境，记录备份时间、schema 版本和 checksum。
2. 执行恢复前快照、恢复、行数/引用完整性检查和导出比对。
3. 随机抽查 100 笔流水、账户余额、预算、订阅和附件引用。
4. 记录 RPO、RTO、丢失条目数、冲突条目数和人工处理时长。
5. 清理隔离数据；演练报告由产品、工程、安全三方签字。

## 事故处理

1. 先判断是否仍在写入：必要时切换只读或停止放量，保留现场日志。
2. 生成当前快照，不覆盖原始备份；保留 requestId、版本和镜像 digest。
3. 若是数据错误，使用数据中心的快照回滚；禁止直接修改生产 SQLite 文件。
4. 若是身份/令牌事件，撤销全部设备会话和集成令牌，轮换代理、WebDAV、邮件和加密密钥。
5. 更新状态页、客服话术和时间线；事后 5 个工作日内完成复盘和修复验证。

## 密钥轮换

- Session、集成令牌和 WebDAV 应用密码只存哈希或当前标签页会话存储，不能进入日志。
- 轮换 `NEO_TRUSTED_AUTH_SECRET` 时先部署能同时接受旧/新签名的短窗口网关，再切换新密钥，最后撤销旧密钥。
- 轮换后执行伪造头、重放 nonce、跨 owner、导出和同步回归测试。
